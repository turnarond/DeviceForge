# v2.14 加固与可见性包设计（#49/#50 收编）

**日期**：2026-10-17 ｜ **基线**：main@c7135d7（v2.13.0 已发版）｜ **票面**：#49（设备任务中心加固包 9 项）、#50（WebSocket 评审不予判断项包 5 子项）

## 1. 背景与复核结论

v2.11 终审与 v2.12 WebSocket 评审入池的加固项，经排痕约定在 v2.14 规划时逐项对照当前代码复核。复核（双路代理取证，证据为文件:行号）结论：

- **#49**：9 项无一被 v2.12/v2.13 波顺带覆盖。7 项仍成立；2 项部分变化——#49-3 校验文案已被 #54 编辑器部分对齐（deploy 分支同口径、commands 分支仍不一致、逻辑未共享），#49-7 对模板 store 不适用（其无内存缓存），但 `DeviceRegistry::save/saveReplacing` 仍内存先行、落盘失败不回滚。
- **#50**：5 子项全部仍成立（数据层 `WsEvent::peer` 已填好、UI 未显示；过滤无控件；token 仍短路比较；丢弃计数语义未交代；运行中配置输入无守卫）。
- **对外文档失实两处**（随 #50 勘误处置）：① v2.12 CHANGELOG 与产品路线图宣称事件流含"对端"列，代码未做（=#50-1）；② 2026-10-15 运营文章把"按方向/主题的事件过滤"写成"v2.13 已立项"，实际 v2.13 未列入也未交付（=#50-2）。

## 3. 波1：单发部署配置存为任务模板（#49-2）

v2.11 spec §4 承诺"现有单次部署入口继续可用，并支持将当前配置保存为新模板"，至今未交付：单发页无任何存模板入口，#54 编辑器的空白新建与 clone 均不构成该条。

### 3.1 入口

`FtpDeployWidget` 工具栏部署组、「▶ 部署」旁新增「保存为模板」按钮：

- tooltip 说明用途（把当前文件/目录/设备选择固化为可复用的任务模板）
- 部署进行中（`m_deployBtn` 禁用态）同步禁用

### 3.2 字段映射（只取模板体系已能表达的字段，不扩模板 schema）

| 单发配置 | 模板承载 | 说明 |
|---|---|---|
| 左面板本地选中文件 + 右面板当前目录 | deploy 步骤 `parameters.files + remoteDirectory` | 编辑器 `collect()` 现有 canonicalize 归一为 `items[]` |
| 协议（ftp/sftp 工具级选择） | deploy 步骤现有协议口径 | 与引擎 `parseDeployItems`/执行通道一致 |
| 设备总线勾选设备 | 模板 `deviceIds` | 未勾选（单发语义=全部设备）→ 留空，编辑器明示"未绑定设备" |
| 「部署后重启」勾选且已配命令 | 预填第二个 reboot 步骤 | 未勾选则只有 deploy 一步 |
| 部署前清空、FTPS/端口、并发度 | **不进模板** | 工具级/连接级配置；模板语义是"部署什么到哪" |

### 3.3 交互与接线

1. 点击按钮 → 复用现有部署前置采集与拒绝分支（左侧为远程浏览源时拒绝、无本地文件时拒绝，文案同部署入口口径）
2. 用预填步骤打开 `TaskTemplateEditorDialog`（与 #54 新建同一对话框），用户补名称/版本
3. 确认后经缝落库：`DeviceForge.cpp` 组装时注入 `std::function<bool(const TaskTemplate&)>`（同 #54 `applyEditorResult` 风格），`FtpDeployWidget` 不直连 `TaskTemplateStore`
4. 落库走 `validateTaskTemplate` 全量校验；同名已存在 → 提示改名或覆盖（沿用 v2.13 导入冲突语义，覆盖继承既有 templateId 与 version 规则）
5. 成功 → 部署页日志「已保存为模板「X」，可在设备任务中心查看」；失败 → 不关对话框、显示 store/校验错误文案

> 执行偏差注记（v2.14 实现期）：落库失败经部署页日志呈现而非重开模态对话框——modal exec() 关闭后回灌用户编辑数据需交互重设计，收益不抵成本；校验失败仍保持对话框内停留（TaskTemplateEditorDialog::accept 闸）。§3.4 落库编排测试相应收敛为存储层 savedId→真名断言 + 部署页模态流人工冒烟。原文保留，本节表述以本注记为准。

### 3.4 测试

## 4. 波2：任务中心加固（#49-1/3/4/7/9）

### 4.1 #49-1 AuthResolver 契约——定档降级语义（已裁定）

不改代码行为。多端点且各端点凭据不同时，任务链凭据**取档案首个可解析引用**并保持现有告警。动作：

- v2.11 spec 增补"凭据解析降级契约"小节（现为 `TaskCenterWidget.cpp` 装配层实现细节，升格为书面契约）
- `TaskCenterWidget.h` 既有注释措辞就实
- CHANGELOG/发布说明如实交代该语义，避免现场误读为多凭据已支持

### 4.2 #49-3 步骤参数校验共享化

现状：引擎 `validateDeviceSteps`（Validating 阶段）与编辑器 `validate()` 两处并行实现；deploy 分支已共用 `deployParamsParseError` 文案，commands 分支不一致（编辑器「至少一条命令」vs 引擎「缺少命令列表」）。

方案：新建纯逻辑头 `src/task/TaskStepValidation.h`（自由函数，返回错误文案或空串通过），承载步骤**参数级**校验（deploy items 解析、commands 非空、reboot 命令可用性）；引擎与编辑器同调，文案单源。`TaskTemplateStore::validateTaskTemplate` 保持只查名称/版本/步骤非空/敏感键，不动。

刻意分工写进头注释与 spec：**端点/设备存在性校验留在执行期**（模板可跨机迁移，导入时端点未必本机存在是 v2.13 定档语义）。

测试：新目标 `tst_task_step_validation`（纯逻辑直测，含 deploy/commands/reboot 三类文案断言）；既有引擎与编辑器用例改断言"文案来自共享函数"防漂移。

> 执行偏差注记（2026-10-17 收口，任务 4 评审裁定）：方案所列「reboot 命令可用性」经分层澄清落地——共享校验层（`TaskStepValidation.h`）对 Reboot 步骤**恒空通过**、不产参数级失败文案（校验期无法预知执行期端点与兜底命令是否可得，硬校验反生误报），不入共享层；可用性兑现由**执行期兜底**承担：引擎 `runCommandStep(rebootMode)` 在 commands 缺失时回退单命令参数、再缺省 `reboot` 命令，仍全空才报「重启步骤缺少命令」。`rebootHasNoParamLevelCheck` 用例锁定校验层恒空形态。原文保留，本节表述以本注记为准。

### 4.3 #49-4 lineage 与 32-run 历史上限错配

现状：引擎 `kHistoryLimit = 32` FIFO 淘汰；widget `m_lineageByEngineRun` 只插不删。会话内超 32 轮后重试旧运行：lineage 命中但引擎以"未知运行 ID"拒绝，widget 笼统报「阶段恢复被引擎拒绝」，未说明真因。

方案（两处小修）：

1. widget 在运行收口时同步淘汰 `m_lineageByEngineRun` 中超限条目（淘汰顺序与引擎 FIFO 同构；上限常量单源——从引擎头公开 constexpr 或经既有接口取，避免魔数复制）
2. 兜底文案（仍命中不了/引擎拒绝时）改为可分辨："该运行的引擎历史已淘汰（超出 32 轮上限），无法阶段恢复"；与真正的"未知运行 ID"区分

测试：tst_task_center_widget 注入 >32 轮收口，断言 lineage 表尺寸钳制与拒绝文案分支。

> 执行偏差注记（2026-10-17 收口，任务 6 裁定）：方案 1 的「收口同步淘汰」实况以**惰性清退**替代——widget 收口时按引擎 FIFO 同构模拟淘汰会把引擎内部实现细节（淘汰顺序）固化为假设、随实现变更漂移（即 §7 风险 1）；改为用户点击「重试」且 `retryFailed` 被拒、`hasRunInHistory(runId)` 证实引擎无存档时，就地清退该运行的 lineage 与 store→engine 映射（点击即校正）。方案 2 的兜底文案落地为 `retryRejectionMessage(lineageKnown, engineHasHistory)` 三分派（本会话外运行/32 轮已淘汰/仍有存档但被拒），上限常量单源（`kHistoryLimit` 上移公开）如期。原文保留，本节表述以本注记为准。

### 4.4 #49-7 DeviceRegistry 落盘失败快照回滚

现状：`save()` 先 `upsert()` 变更 `m_profiles` 再写 ConfigStore，失败仅 qWarning + return false；`saveReplacing()` 同型（先改内存、落盘失败直接返回，清扫只在成功后走）。内存与磁盘分叉。

方案：变更前排快照 → 落盘失败恢复快照再返回 false。范围仅 `m_profiles` 受影响条目的差量（插入/更新/删除），不做全表深拷贝；`saveReplacing` 的清扫与内存变更顺序保持"落盘成功才清扫"。

> 说明：票面原文点名的 `TaskTemplateStore::save/saveReplacing` 经复核**不适用**——该 store 无内存缓存、save 直写 ConfigStore，本项对象为 DeviceRegistry。票关闭时在票内留此勘误。

测试：tst_device_registry 注入 ConfigStore 失败面（临时库置只读或既有失败注入缝），断言 save/saveReplacing 失败后内存态与失败前逐字段一致、且未发生清扫副作用。

### 4.5 #49-9 引擎异常路径 error.what() 未过脱敏

现状：正常错误路径已统一过 `sanitizeTaskErrorText`，但协调线程 Runnable catch 与执行收口 catch 两处把原始 `error.what()` 直送 qWarning→LogBridge→全局日志。适配器异常文本可能含 URL/凭据片段。

方案：两处 catch 的 `what()` 先过 `sanitizeTaskErrorText` 再入日志/记录，与正常路径同口径。

测试：tst_task_execution_engine（或既有引擎目标）构造异常文本含敏感形态（user:pass@host），断言日志出口只见脱敏后文本。

## 7. 风险与开放点

| 风险 | 处置 |
|---|---|
| lineage 同步淘汰依赖"引擎 FIFO 顺序"假设，引擎内部实现若变会漂移 | 上限常量单源 + 用例锁定淘汰顺序假设，引擎头注释指回 |
| DeviceRegistry 差量快照在 saveReplacing 多条目替换下的快照粒度 | 计划期先读 saveReplacing 现状定快照范围，倾向"整表浅快照（id→profile 映射）"以保简单 |
| 常量时间比较在 -O2 下可能被优化短路 | 用 volatile 读累差实现，注释说明；tst_ws_loopback 只验行为不验时序（时序断言不可靠，如实标注） |
| 单发页「保存为模板」与设备总线"未勾选=全部"的语义鸿沟 | 编辑器明示未绑定设备，不做隐式展开为全部设备 id（跨机时"全部"不可移植） |
