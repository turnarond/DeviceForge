# 需求：NetRelayTool 组播增强（实时转发 + 易用性）

- 版本目标：v2.8 候选
- 提出人 / 日期：用户 2026-08-21（修订版：撤销"广播"需求，聚焦组播增强）
- 关联 issue：无
- 关联设计：`docs/03-设计/方案设计/2026-07-10-组播录制回放设计.md`（组播抓收/录制/回灌，已落地）

> 历史：本需求首版为「广播抓收/录制/回灌」（2026-08-21），经用户澄清**撤销**——现场不需要广播，只需要组播。本文档修订为组播增强。

## 背景与动机

NetRelayTool 已支持组播（Multicast）**单向抓收 + 录制 + 回灌**（2026-07-10 设计落地）。现场使用反馈：
1. **「不会用、不好用」**：UI 无协议联动（选 Multicast 界面零变化）、「监听地址/端口」无效却可编辑、组播组地址藏在「上游地址」输入框、回放面板「消费者 127.0.0.1:9001」对组播语义误导；
2. **「组播是否支持转发？」**：当前实现**只抓不转**（抓收是旁路抄收，不是转发）——设计阶段将「转发」列为 YAGNI，但现场存在把抓到的组播流**实时转发**给其他组/消费者的诉求。

## 需求描述（用户视角）

1. **抓包录制**（已有，保持）：加入组播组零影响抄收 → Hex 查看 → 录制 `.nrec`
2. **实时转发（新增）**：抓收组播流的同时，**能转发则转发**——把收到的数据报实时转发到：
   - 另一个组播组（M→M），或
   - 指定单播消费者（M→U，待确认）
3. **回灌**（已有，保持）：离线按原时序回灌原组
4. **易用性（新增）**：协议联动（抓收模式隐藏无效控件、标签语义化）、回放面板对组播语义正确提示

## 边界

- **In**：IPv4 组播（224.0.0.0~239.255.255.255）抓收/录制/回灌；组播→组播 与/或 组播→单播 实时转发（形态待确认）；UI 易用性修复
- **Out（本期不做，YAGNI）**：
  - 广播（用户明确不需要）、IPv6 组播、二层组播
  - 单播→组播 转发（反向）
  - 组播源在线检测/自动防混叠（技术上不可靠，仅提示）

## 验收标准（可测）

1. 协议下拉选 Multicast 后：监听地址/端口隐藏或禁用，目标标签显示「组播组地址」，placeholder 提示 `239.1.2.3`
2. 抓收（已有行为不回归）：加入组 → Hex 实时显示 → 录制 → 回灌原组
3. **转发**：工具抓收 A 组时，B 组接收器（或指定单播接收器）实时收到与 A 组一致的转发数据；转发不中断抓收/录制
4. 转发可开关（勾选），停止转发不影响抓收
5. 旧 `.nrec`（TCP/UDP/Multicast）读取回放不回归
6. 长稳：转发 + 抓收 + 录制长时间运行无内存/句柄泄漏、无 socket 泄漏（重复启停）

## 非功能要求

- **零影响**（抓收）：加入组不抢占端口、不影响现有消费者（沿用 ShareAddress|ReuseAddressHint）
- **转发安全**：M→M 转发到目标组前 UI 确认（目标组可能有真实源/环路风险）；转发与回放互斥（复用 RelayMode 状态机）
- **长稳**：转发链路复用背压/缓冲策略；重复启停资源归零
- **性能**：高频组播转发不丢包不卡 UI

## 优先级
