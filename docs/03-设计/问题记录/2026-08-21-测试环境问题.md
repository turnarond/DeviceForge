## 结论摘要（2026-08-21 解决）

**根因**：CMake 全局强制 `/MD + _ITERATOR_DEBUG_LEVEL=0`（对齐预编译 lw 库），而 Qt Debug 库（Qt6Cored.dll 等）为 `/MDd + IDL=2` 构建——Debug 配置下 exe 链接 debug Qt，跨 DLL 边界的 std 类型（`QString::toStdWString/toStdString/fromStdString`）ABI 错位：
- **启动崩溃**：`LocalFileSource::list` 的 `fs::path(path.toStdWString())` → `std::wstring::_Deallocate` 堆损坏（0xC0000374），最小复现程序确凿验证
- **7 个 Debug 测试失败**（config_store/sftp_plan/deploy_loop/remote_model/file_source/panel_async/telnet_timeout）：std::string 乱码/SEGFAULT/堆损坏

**解决（方案 A）**：CMakeLists `set_target_properties(... MAP_IMPORTED_CONFIG_DEBUG RELEASE)`——**Debug 配置也链接 Release Qt 库**（Qt6.dll），exe / lw 库（预编译 /MD）/ Qt 三者 CRT 全一致（/MD+IDL=0）。代价：Debug 下不能单步 Qt 库内部（应用代码调试不受影响）。另：根 find_package 补 `Test` 组件（否则 Qt6::Test 不被映射，tst_panel_async 混链 Qt6Testd.dll）。

**验证**：DeviceForge Debug 编译通过；smoke 启动主窗口正常出现；**ctest Debug 16/16 全绿**（原 7 个失败全部恢复）；LocalFileSource 同时加了 `toFsPath()`（QByteArray 中转）防御性修复。

**遗留**：Release 全量编译在本机存在环境问题（cl 长时间无产出，与代码无关），建议在用户环境/CI 验证。

## 问题 1：Debug 配置下 7 个测试失败（std::string ABI 错位 / SEGFAULT / 堆损坏）

### 现象（`ctest -C Debug`）

| 测试 | 结果 |
|------|------|
| tst_config_store | SEGFAULT |
| tst_sftp_plan | 0xc0000374（堆损坏） |
| tst_deploy_loop | Failed |
| tst_remote_model | Failed（`fileAt(0).name` 读回 `"\u0000..."` 乱码） |
| tst_file_source | 0xc0000374（堆损坏） |
| tst_panel_async | 0xc0000374（堆损坏） |
| tst_telnet_timeout | SEGFAULT |

### 关键事实

- **Release 配置下上述 7 个测试 6 个通过**（tst_remote_model/tst_config_store/tst_panel_async/tst_file_source/tst_sftp_plan/tst_telnet_timeout 全 Passed），仅 tst_deploy_loop 因 DLL 缺失失败（见问题 2）。
- 失败特征高度一致：std::string/容器内存错位、堆损坏、段错误——典型 **ABI 不匹配**症状。
- 已排除：FtpFileInfo 双定义（`src/adapter/FtpAdapter.h` 仅为前向声明，唯一定义在 `src/tools/FtpDeployTool/FtpFileInfo.h`）。
- CMake 已强制 `/MD`（`CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreadedDLL`）+ `_ITERATOR_DEBUG_LEVEL=0`（CMakeLists.txt:20,32）。

### 疑点（待排查）

Debug 配置使用 `/MD`（Release CRT）+ Debug 版 Qt DLL 的组合下，`std::string` 在 **Qt DLL 边界**（QString::fromStdString 等）或 CRT 边界上的布局是否一致。重点核查：
1. 测试链接的 Qt 库是 debug 版（Qt6Cored.dll）还是 release 版——若 Qt 以 debug 库编译而 CRT 是 release（/MD），跨 DLL 传 `std::string`（如 `QString::fromStdString` 传 C 指针则安全，但若有跨 DLL 的 std::string 参数/返回值则 ABI 不匹配）。
2. 各测试目标是否混链了不同配置的 thirdparty 静态库。

### 建议

- 后续专门排查（可在 CI 的 Release 配置跑测试作为红线；Debug 配置下先以 Release 为准）。
- 若确认是 Debug+Qt 库组合问题，可在 CI 中仅跑 Release 测试，或为 Debug 配置统一 `/MDd` + IDL=2 并配套调整。

## 问题 2：tst_deploy_loop（Release）0xc0000135 DLL 缺失

### 现象

`ctest -C Release -R tst_deploy_loop` 报 `Exit code 0xc0000135`（STATUS_DLL_NOT_FOUND）。

### 分析

- `build/Release/` 输出目录在仅构建 tests 目标时**无任何 DLL**（libcurl-x64.dll / libssh2.dll / Qt DLL 均未复制）。
- CLAUDE.md 说明 POST_BUILD 会把 DLL 复制到 DeviceForge 输出目录——**仅在构建 DeviceForge 目标时触发**；只构建 tests 目标时 DLL 缺失。
- tst_deploy_loop 依赖 libcurl 相关（部署循环 mock），缺少 `libcurl-x64.dll`（或 Qt DLL 依赖链）时启动失败。

### 建议

- 为 tests 目标补充 DLL 复制（或文档说明：先构建 DeviceForge 再跑测试）。
- 与问题 1 一起在 CI 流程中验证：`cmake --build . --config Release`（全量）后再 `ctest -C Release`。
