# FTP QUOTE 响应写入失败与批量部署重试

## 现象

三台设备批量部署同一文件时，偶发一台设备在临时文件原子提交阶段失败；手动点击“重传失败设备”后通常成功。典型日志为：

```text
上传失败: 重命名失败: Failed writing received data to disk/application
```

## 根因

`FtpAdapter` 使用 `CURLOPT_QUOTE` 执行 `RNFR/RNTO`、`DELE`、`RMD` 和 `MKD` 时没有设置响应写回调。libcurl 会尝试使用默认标准输出处理 FTP 响应；在 GUI 进程或不同 FTP 服务端响应格式下，可能返回 `CURLE_WRITE_ERROR`。

同时，传输错误分类此前没有将该类 libcurl 瞬时写入错误标记为可重试，因此单台设备会直接进入失败终态，而不会自动重连重试。

## 修复

- 上传及所有 FTP QUOTE 操作统一接入内存响应缓冲，禁止默认写入标准输出。
- 将 `Failed writing received data`、`Couldn't write received data` 和 `write error` 归类为可重试的远端 I/O 错误。
- 保持权限、认证、路径等确定性错误不可重试，避免无效重试。

## 验证

- `tst_transfer_types`：8/8 通过，覆盖瞬时写入错误的可重试分类。
- `tst_transfer_channel`、`tst_transfer_executor`、`tst_transfer_scheduler`、`tst_deploy_loop`、`tst_deploy_runner`：6/6 通过。
- 现场复测三台设备批量部署同一文件：结果基本正确且运行稳定；单台瞬时失败可通过自动重连重试恢复，未再依赖手动重传。
