# DeviceForge v2.8 发布闭环设计

**日期**：2026-09-01 ｜ **状态**：待评审 ｜ **范围**：发布治理，不修改运行时产品功能

## 1. 背景

`v2.8.0` 已在 `origin/main` 的 `a6e9283` 打 Tag，代码已包含并行批量部署、设备级进度、CSV/HTML 报告和失败重试，CTest 目标也扩展到 20 个。但发布治理没有同步闭环：CI 工作流从仓库中消失，`.gitignore` 仍忽略 `.github/`；白皮书、两份路线图和 Release Notes 停留在旧版本语义；v2.8 设计仍标记“草案（待评审）”，实施计划的复选框未回填；16 台模拟、50 轮句柄基线等长稳验收没有正式证据。

本设计只修复发布流程、文档事实源和验收入口。已发布 Tag 不移动、不覆盖；无法在当前环境重现的验证不写成“已通过”。

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 | 验收标准 |
|---|---|---|
| G1 | 恢复持续集成 | push/PR 到 `main` 时，Windows Debug/Release 均配置、构建并运行全部 CTest；Python 工具测试和版本一致性检查为阻断步骤 |
| G2 | 建立可重复的发布验收入口 | 提供手动触发的 Windows Release 工作流，完成构建、CTest、UI 冒烟、运行时部署和 NSIS 打包，并上传构建/安装包产物 |
| G3 | 扩展版本一致性校验 | `versioncheck.py` 同时校验根 Roadmap、产品路线图、Release Notes；缺失强制来源也必须失败 |
| G4 | 消除 v2.8 文档语义漂移 | README、白皮书、两份路线图、Release Notes、CHANGELOG 对 v2.8 的功能与版本边界一致 |
| G5 | 回填 SDD 状态与验收证据 | v2.8 设计、实施计划和新验收报告区分“代码已实现”“自动验证通过”“人工/长稳待执行” |
| G6 | 保护本地隔离开发 | `.gitignore` 不再忽略 `.github/`，并忽略 `.worktrees/` |

### 2.2 非目标

- 不实现 SCP、ToolHost、多语言、Linux 或新的协议能力。
- 不修改 `DeployJob`、`DeploymentRunner`、FTP/SFTP 等运行时代码。
- 不移动或覆盖已发布的 `v2.8.0` Tag。
- 不把缺少日志或测试输出的手工验证标记为完成。
- 不在本轮建设真实 FTP/SFTP 服务端集成测试或完整长稳平台；它们作为后续可靠性版本的独立需求。

## 4. 总体方案

### 4.1 日常 CI

新增 `.github/workflows/ci.yml`：

1. 触发：push/PR 到 `main`，以及手动触发。
2. 环境：`windows-latest`、Qt 6.9.2、Python 3.12。
3. Python 阶段：运行 `python -m unittest discover -s tools/tests -v` 和 `python tools/devtools/versioncheck.py`。
4. C++ 阶段：使用 Debug/Release 矩阵分别配置、构建并执行 `ctest --output-on-failure`。
5. Qt 6.9.2 保留为最低兼容基线；正式本地开发版本继续为 Qt 6.11.1，文档明确双版本职责。

CI 不生成正式 Release 包，避免日常 PR 因 GUI 冒烟或打包工具造成不必要的波动。

### 4.2 手动发布验收工作流

新增 `.github/workflows/release-validation.yml`，仅 `workflow_dispatch` 触发：

1. 校验输入版本与 `CMakeLists.txt` 权威版本一致。
2. 配置并构建 Release。
3. 运行全部 CTest、Python 工具测试和 `versioncheck.py`。
4. 执行 `windeployqt`，补齐 Qt DLL 与插件。
5. 运行 `smoke.py`；若 GitHub Windows Runner 无可交互桌面导致窗口枚举失败，工作流必须失败并保留日志，不得静默跳过。
6. 安装 NSIS 3.x，执行 `makensis /DVERSION=<version> packaging/deviceforge.nsi`。
7. 上传解压版目录和 NSIS 安装包为工作流产物。

该工作流是“可重复验收入口”，不是自动发布到 GitHub Releases；对外发布仍需人工确认验收报告后执行。

## 5. 版本一致性工具

### 5.1 新增校验来源

在 `tools/devtools/versioncheck.py` 增加：

- `RELEASE_NOTES.md`：解析标题 `# DeviceForge vX.Y.Z Release Notes`。
- `ROADMAP.md`：解析 `**当前版本**：vX.Y.Z`。
- `docs/01-白皮书/产品路线图.md`：新增并解析同格式当前版本字段。

这些来源与现有 CMake、RC、README、CHANGELOG、CLAUDE、白皮书一起成为发布强制来源。

### 5.2 缺失文件语义

当前实现把非权威来源缺失记录为 warning，仍返回成功。发布校验中这会让 Release Notes 或 Roadmap 被删除而不阻断发布。本轮改为：任一强制来源缺失或无法解析，`consistent=false`，CLI 返回非零。

### 5.3 TDD 用例

先在 `tools/tests/test_versioncheck.py` 添加并观察失败：

- Release Notes 版本解析。
- 根 Roadmap 版本解析。
- 产品路线图版本解析。
- 任一强制来源缺失时校验失败。
- 三类新来源与 CMake 不一致时分别进入 `mismatches`。

随后最小修改生产代码使测试通过，并运行完整 Python 测试集。

## 8. 安全、兼容性与回滚

- 不修改运行时功能和公开 C++ 接口，无 ABI 影响。
- CI 使用只读 `contents: read` 权限；发布验收工作流只上传 Actions artifact，不创建 Release、不写仓库。
- 第三方 Action 固定主版本，并限定到必要的 checkout、Python、Qt 和 artifact 功能。
- 回滚方式为整体回退本治理分支；`v2.8.0` Tag 不受影响。
- `.github/` 从 `.gitignore` 移除后，工作流必须显式纳入 Git 跟踪；`.worktrees/` 保持忽略，避免本地隔离目录污染状态。

## 9. 验证矩阵

| 层级 | 命令/入口 | 阻断条件 |
|---|---|---|
| Python 单元测试 | `python -m unittest discover -s tools/tests -v` | 任一失败 |
| 版本一致性 | `python tools/devtools/versioncheck.py` | 缺失、无法解析或版本不一致 |
| C++ Debug | `cmake --build build --config Debug` + CTest | 配置、构建或测试失败 |
| C++ Release | `cmake --build build --config Release` + CTest | 配置、构建或测试失败 |
| GUI 冒烟 | `python tools/devtools/smoke.py <DeviceForge.exe>` | 未出现主窗口、提前退出或无法优雅关闭 |
| 打包 | `makensis /DVERSION=2.8.0 packaging/deviceforge.nsi` | 缺文件或编译失败 |
| 长稳 | 16 台模拟、50 轮，记录资源基线与终值 | 资源持续增长、线程/连接未归零或无证据 |
