# DeviceForge v2.9 快速启动与懒加载设计

**日期**：2026-09-09 ｜ **状态**：方案评审通过
**上位蓝图**：`2026-09-09-v2.9-现场工作台蓝图.md`

## 1. 问题

当前 `window.show()` 前同步打开 ConfigStore、初始化 curl/libssh2、加载完整 QSS，并构造六个 Backend 与 Widget。任何 Tool 的构造成本都会阻塞首窗出现。

## 2. 三阶段启动

### Bootstrap

创建 QApplication、安装日志桥、读取主题/窗口几何/最后工作区等最小配置，并注册轻量工作区描述。

### First Frame

只构造主窗口外壳、固定设备上下文、导航、空工作区容器和日志区，应用首屏必需主题后立即 `show()`。

### Deferred Ready

事件循环启动后加载默认文件工作区；其余工作区首次点击时创建并缓存。curl、libssh2、open62541 等协议能力首次使用时线程安全初始化。OTA 自动检查、非关键配置恢复在首帧后执行。

## 3. 工作区生命周期

主窗口维护工作区描述表：ID、名称、图标、顺序、创建工厂和状态。状态机为：

```text
NotLoaded → Loading → Ready
                    └→ Failed → Loading（用户重试）
```

快速连续点击不得重复创建。创建失败显示原因和“重试加载”，不影响其他工作区。已加载实例常驻到退出；本期不做卸载。

## 4. 初始化与退出

- 协议全局初始化使用一次性线程安全入口；失败保存稳定错误，禁止半初始化 Adapter 继续工作。
- QWidget 与轻量结构仍在 GUI 线程创建；目录读取、连接探测等重操作延后到首帧后异步执行，结果通过安全队列回到主线程。
- 退出顺序：停止接收任务 → 取消并等待传输收口 → 停止已加载工作区 → 关闭 ConfigStore。
- 从未加载的工作区不参与退出。
- 主题原则上在首帧前应用。若测量确认完整 QSS 是瓶颈，则拆为基础 QSS 和延迟补充 QSS，但不得出现无样式闪烁。

## 5. 启动度量

新增轻量 `StartupTracer`，记录进程入口、最小配置读取完成、主窗口构造完成、首次 show、默认工作区可操作和各工作区首次加载耗时。

同一台测试机对 v2.8 与 v2.9 各执行冷启动、热启动 10 次。验收目标：首窗可见时间至少降低 50%；热启动中位数优先压到 500 ms 以内；默认工作区加载期间窗口可拖动、重绘并响应输入。

## 6. 测试

- 工作区只创建一次、失败可重试、连续点击无重入。
- 未加载 Tool 不启动线程、不创建 socket、不读取业务配置。
- 默认工作区加载时 GUI 心跳持续响应。
- 关闭发生于传输、工作区加载或协议初始化失败期间时，资源仍确定性回收。
- 启动报告可重复生成并与 v2.8 基线比较。
