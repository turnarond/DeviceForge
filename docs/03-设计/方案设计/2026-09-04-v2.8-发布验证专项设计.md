# v2.8 发布验证专项设计

## 1. 目标与边界

本专项用于完成 v2.8 发布验证闭环，优先解决构建、打包、portable Smoke 和证据复现问题。

本批次只修改工作流、测试工具、打包脚本和验收文档，不修改 `src/`、公开 ABI 或产品运行时功能。若验证暴露运行时缺陷，另立独立修复任务，并在修复后重新执行完整证据链。

## 2. 验收流水线

流水线按以下顺序执行，任一步骤失败即停止：

`输入版本 → 9 源版本门禁 → Debug/Release 构建 → CTest → windeployqt → portable ZIP → 隔离环境解压 → 清理 Qt SDK 环境 → Smoke → 上传 ZIP 与日志`

NSIS 安装包因现有递归卸载语义存在安全风险，本专项不编译、不上传、不分发 NSIS artifact，待独立 PATCH 完成安全卸载清单和目录校验后再评估恢复。

真实 FTP/SFTP、3 台本地 ftpd 模拟器和 16×50 长稳测试属于后续人工证据阶段，沿用同一验收报告格式，不在本专项中伪称完成。

## 3. 组件职责与数据流

- `.github/workflows/release-validation.yml` 负责 Windows runner 上的顺序编排、失败即停和 artifact 上传。
- `tools/devtools/versioncheck.py` 是唯一版本一致性判定入口，强制校验 9 个版本来源。
- `tools/devtools/smoke.py` 只接收解压后的 EXE 路径，负责启动、窗口识别、关闭和进程清理，不负责构建或安装环境。
- `tools/tests/test_release_governance.py` 静态锁定 portable-only、无 NSIS 上传、Smoke 环境隔离和输入校验。
- 验收报告区分“自动通过”“人工待执行”“环境阻塞”“安全阻塞”，每项记录命令、环境、时间、退出码和日志或 artifact 路径。

工作流生成版本化 ZIP 和运行日志；Smoke 只消费 ZIP 解压目录。报告只引用实际运行记录，不从本地历史结果推断远程通过。

## 4. 失败处理

- 版本门禁失败：立即停止，不进入构建。
- 构建或 CTest 失败：保留完整日志，不生成可发布 artifact。
- Qt 部署失败或必需插件缺失：阻断 ZIP 验收。
- Smoke 失败：保留解压目录摘要、退出码和进程清理结果，不标记发布通过。
- 缺少 `_ctypes`、NSIS 或真实设备：记录为环境或安全阻塞，不降级为成功。
- 发现运行时产品缺陷：从专项分叉独立修复任务，修复后重跑完整证据链。

## 5. 测试与成功标准

测试分三层：

1. 静态治理测试：验证 YAML、artifact、环境清理和输入约束。
2. 本地工具测试：运行全部 Python 测试、版本门禁和 Smoke 单元测试。
3. 远程验收：运行 GitHub Actions 首次验收，确认 Qt 6.9.2、VS2022 runner 与本地证据边界一致。

专项成功标准：远程工作流全绿；只产生 portable ZIP；Smoke 在隔离环境实际通过；验收报告可由第三方按记录的命令复现。未完成的真实设备、长稳和 NSIS 项目必须保持明确阻塞状态。

## 6. 交付顺序

1. 触发并记录 GitHub Actions 首次运行。
2. 确认 portable ZIP 解压 Smoke 使用隔离 Qt 环境。
3. 对失败项做最小范围修复并重跑证据链。
4. 回填验收报告，保留未完成项目和阻塞原因。
