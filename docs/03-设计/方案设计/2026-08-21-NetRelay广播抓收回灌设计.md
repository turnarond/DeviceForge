- **日期**：2026-08-21
- **状态**：待评审（SDD 阶段 1 强制门禁，评审通过后进入实施）
- **需求来源**：`docs/02-需求分析/2026-08-21-NetRelay广播抓收取录回灌.md`
- **前序设计**：`docs/03-设计/方案设计/2026-07-10-组播录制回放设计.md`（组播方案，本设计为其姊妹扩展）
- **模块**：`src/tools/NetRelayTool/`

## 1. 背景与目标

组播方案（2026-07-10）已实现「加入组抄收 + 录制 + 回灌原组」。现需补齐**广播（broadcast）**同等级能力：
抓收发往 `255.255.255.255` / 子网定向广播（`a.b.c.255`）的数据报 → Hex 查看 → 可选录制 `.nrec` → 按原时序回灌原广播地址/端口。

**关键差异（广播 vs 组播）**：
- 组播是**订阅制**（IGMP join，工具作为额外订阅者加入）；广播是**无差别收**（广播域内所有主机都收，工具只需 bind 端口即可接收，**无需 join**）
- 组播地址是 D 类（224-239）；广播地址是 `255.255.255.255` 或子网定向广播（最后 8 位全 1）
- 广播**发送**（回灌）需 `SO_BROADCAST` 选项；组播发送则不需要
- 定向广播与网卡强相关（发往哪个子网的广播须从该网卡发出）

## 2. 架构决策（本次评审核心）

### 2.1 决策 A：协议枚举扩展 + 抓收通道收敛（推荐）

**现状问题**：`NetRelayBackend` 中 `startMulticastCapture()`（组播抓收）与 UDP 中继路径（`m_udpListen` + 会话表）是**两套并行实现**；协议分支（校验/bind/清理）散落。若广播继续叠 if-else，将出现第三套相似代码。

**方案**：
1. `NetRelayTypes.h`：`RelayProtocol` 增加 `Broadcast`（枚举值 3）
2. Backend：把 `startMulticastCapture()` 重构为通用 **`startCapture(RelayProtocol proto, targetAddr, port, ifaceAddr)`**，`Multicast | Broadcast` 共用抓收通道：
   - 共享：`m_captureSocket`（原 `m_mcastSocket`）、bind（`AnyIPv4 + ShareAddress|ReuseAddressHint`）、readyRead 收包、录制、清理、`RelayMode` 状态机
   - 差异（收敛为两个小分支）：
     - **地址校验**：`multicastAddrValid()`（D 类）vs `broadcastAddrValid()`（有限/定向广播）
     - **加入组**：组播 `joinMulticastGroup(group, iface)`；广播**跳过 join**（无订阅概念）
3. UDP 中继（双向转发）路径**保持不动**（`startRelay(Udp, ...)`）——抓收通道与中继通道语义不同（单向抓 vs 双向转发），不强行合并，避免大重构风险

> 收益：广播实现 ≈ 20 行差异（校验 + 跳过 join），其余全部复用；消除组播/UDP 双路径的重复（bind 校验、清理代码收敛）。
> 风险：`startCapture` 重构涉及既有组播路径，需回归组播抓收/录制/回放（tst_nrec + 手动）。

### 2.2 决策 B（备选，不推荐）：继续 if-else 扩展

在现有 `startMulticastCapture` 内加 Broadcast 分支。改动最小但代码继续膨胀（校验/bind/日志各再叠一套），`m_mcastSocket` 语义混乱（组播和广播共用却叫 mcast）。**不采用**。

## 3. 广播抓收（Backend）

```cpp
// 地址校验（纯逻辑，可单测）
bool multicastAddrValid(const QString& addr);   // 224.0.0.0~239.255.255.255（现有逻辑提取）
bool broadcastAddrValid(const QString& addr);   // 255.255.255.255 或 a.b.c.255（最后 8 位全 1，非 D 类）

// 抓收入口（重构自 startMulticastCapture）
void startCapture(RelayProtocol proto, const QString& targetAddr, quint16 port, const QString& ifaceAddr);
```

- **bind**：`QHostAddress::AnyIPv4` + `ShareAddress | ReuseAddressHint`（沿用组播经验：Windows 只认 `ReuseAddressHint`，缺它独占端口破坏"零影响"）
- **接收广播**：bind 后 `readyRead` 直接收——**无需任何 socket 选项**（`SO_BROADCAST` 仅发送必需）；Windows 下绑 `AnyIPv4:port` 即可收到有限广播与子网广播
- **网卡**：定向广播抓收建议在文档说明（若多网卡收不到，可后续增强为 bind 指定网卡地址——本期先用 AnyIPv4 + 网卡下拉仅用于回灌/组播 join，抓收不 bind 网卡；详见 §6 风险）
- **方向/会话**：与组播一致——单向恒 `Upstream`，会话号固定 1，会话列表显示为「抓收通道」
- **录制**：`RelayRecorder::open(path, RelayProtocol::Broadcast, epoch, targetAddr, port)`——复用现有 protocol/groupAddr/groupPort 参数

## 4. `.nrec` 格式兼容（关键）

| 项 | 现状（组播） | 广播扩展 |
|---|---|---|
| protocol 字段 | Tcp=0 / Udp=1 / Multicast=2 | **新增 Broadcast=3** |
| 目标地址/端口 | reserved 偏移 16-31（group_port u16 + group_addr 字符串） | **复用同一 reserved 布局**存广播地址/端口 |
| 版本 | kVersion=1 | **不变**（reserved 字段布局不变，仅 protocol 值新增） |

**读取端必须修改**（`RelayRecording.cpp` 当前 `proto != 0/1 → Multicast` 的兜底会误判 proto=3）：
```cpp
out.protocol = (proto == 0) ? Tcp : (proto == 1) ? Udp : (proto == 2) ? Multicast : Broadcast;
```
- 旧文件（0/1/2）读取不受影响（显式分支，不再用 else 兜底）
- 回放端 `RelayPlayer::start()` 增加 Broadcast 分支（§5）

## 5. 广播回灌（RelayPlayer）

```cpp
else if (m_protocol == RelayProtocol::Broadcast) {
    m_udp = new QUdpSocket();
    if (!m_mcastIfaceAddr.isEmpty()) {
        // 定向广播从指定网卡发出：bind 到该网卡 IP（发送 socket 绑定源地址）
        m_udp->bind(QHostAddress(m_mcastIfaceAddr), 0);
    }
    m_udp->setSocketOption(QAbstractSocket::BroadcastSocketOption, 1);  // SO_BROADCAST，发送必需
    m_connected = true;
    scheduleNext();
}
// sendCurrent 中：writeDatagram(payload, m_consumerAddr, m_consumerPort)
```

- 目标地址默认取 `.nrec` 文件头（原广播地址/端口），可被 UI 覆盖（复用现有覆盖逻辑）
- 有限广播 `255.255.255.255`：从默认网卡发出（无需 bind 网卡）；定向广播 `a.b.c.255`：若用户选了网卡则 bind 该网卡
- 回灌前 UI 二次确认「真实源须离线」（与组播回灌一致，Broadcast 同样适用）

## 9. 风险与对策

| 风险 | 对策 |
|------|------|
| Windows 收广播绑 AnyIPv4 是否必收子网广播 | 主路径支持有限广播（`255.255.255.255`，确定可收）；子网定向广播在多数网卡上可收；若个别网卡收不到，抓收可增强为 bind 指定网卡 IP（预留，回灌已支持网卡 bind） |
| startCapture 重构回归组播 | tst_nrec 组播用例 + 手动组播抓收验证 |
| `.nrec` proto=3 被旧读取逻辑误判 | 读取端显式分支 + legacy 回归测试 |
| 回灌广播导致广播风暴/影响现场 | 回灌为人工操作 + 二次确认提示；默认回灌原地址/端口 |
| 多网卡定向广播收/发不一致 | 抓收先用 AnyIPv4（文档说明局限）；回灌支持网卡 bind；后续按需增强 |

## 10. 非目标（YAGNI，与组播方案一致）
