# DeviceForge v2.10 批量命令与部署后重启设计

**日期**：2026-09-28  
**状态**：设计评审中  
**目标版本**：v2.10.0

## 1. 背景与问题

当前工程已经有“批量命令”界面和 Telnet/SSH 适配器，但命令执行逻辑主要位于 `TelnetBackend`。文件部署完成后的“部署后重启”选项在 `FtpDeployBackend` 中只有日志占位，没有真正向设备发送重启命令。

这导致两个问题：

1. 批量命令能力不能被文件部署流程复用；
2. 部署成功后无法自动重启设备，且没有逐设备的重启结果。

## 2. 目标与非目标

### 2.1 目标

- 提供统一的 Telnet/SSH 批量命令执行内核。
- 批量命令工具与“部署后重启”共用同一执行内核。
- 支持多台设备、多个命令、逐设备结果、超时、取消和失败重试。
- 部署后只对文件部署成功的设备发送重启命令。
- 将“命令已发送/设备主动断开”视为重启命令的正常终态，不要求重启连接保持。
- 保留现有设备栏凭据来源，不新增明文密码存储。

### 2.2 非目标

- v2.10 不实现交互式终端、命令补全或脚本语言。
- v2.10 不改变 Telnet/SSH 底层认证协议。
- v2.10 不实现设备在线探测或重启完成后的自动重新上线确认；该能力作为后续版本扩展。

## 3. 方案选择

### 方案 A：部署后直接调用 `TelnetBackend`

改动最少，但文件部署后端会依赖命令工具后端，形成 Tool 间反向耦合，无法清晰表达重启结果，不采用。

### 方案 B：抽取共享 `BatchCommandRunner`（推荐）

在 UI 与 ToolBackend 之下新增命令执行服务。批量命令工具和文件部署后端都提交命令任务，由服务统一创建适配器、连接设备、执行命令、处理超时和取消。该方案职责清晰，可测试性和后续扩展最好。

### 方案 C：调用外部脚本

能够快速适配厂商命令，但难以统一逐设备状态、凭据擦除、取消和重试语义，不采用。

## 4. 总体架构

```text
TelnetWidget ───────┐
                     ├─ BatchCommandRunner ── ProtocolRegistry ── TelnetAdapter
FtpDeployBackend ───┘                         └────────────────── SSHAdapter
```

建议新增：

- `src/command/BatchCommandRunner.h/.cpp`：命令任务调度和逐设备执行。
- `src/command/CommandTypes.h`：命令请求、设备结果、批次汇总和回调类型。
- `tests/command/tst_batch_command_runner.cpp`：使用 fake adapter 验证执行、失败、取消和重试。

`TelnetBackend` 保留现有 Tool 生命周期和 UI 回调，只负责把界面输入转换为 `BatchCommandRequest`。`FtpDeployBackend` 在部署报告生成后构造重启请求，不直接操作 Telnet/SSH 适配器。

## 5. 命令任务模型

```text
BatchCommandRequest
├── protocol: telnet | ssh
├── devices: DeviceInfo[]
├── auth: AuthInfo
├── commands: string[]
├── timeoutSec
├── retryCount
├── retryDelayMs
└── cancelFlag
```

逐设备结果至少包含：

- 设备标识（IP 和端口）；
- 连接结果；
- 已执行命令数；
- 是否成功；
- 是否属于“命令发送后连接断开”的正常重启终态；
- 输出摘要和脱敏错误信息；
- 耗时和重试次数。

密码只在任务生命周期内存在，任务结束后调用 `AuthInfo::clear()`，日志不输出用户名密码或命令返回原文中的敏感字段。

## 6. 部署后重启流程

```text
DeploymentRunner 完成
        ↓
收集 DeviceResult::Ok
        ↓
构造 BatchCommandRequest
        ↓
按配置选择 Telnet/SSH 与重启命令
        ↓
逐设备连接并发送命令
        ↓
记录 RebootResult
        ↓
生成部署 + 重启汇总
```

部署失败、取消或预检失败的设备不会进入重启列表。默认重启命令为 `reboot`，用户可以配置为 `shutdown -r now` 或设备厂商命令。发送命令后若设备立即关闭连接，若已收到命令写入成功或协议层确认，则标记为“重启已触发”，不将断开误报为失败。

部署界面新增配置：

- 重启协议：Telnet / SSH；
- 重启命令：默认 `reboot`；
- 命令超时：默认 10 秒；
- 失败重试次数：默认 1 次；
- 是否在部署完成后执行。

配置通过 `ConfigStore` 持久化，不使用 `QSettings`。

## 7. 批量命令界面调整

现有批量命令界面继续保留，改为调用 `BatchCommandRunner`。界面增加：

- 重试次数和命令间隔配置；
- 设备级状态：等待、连接中、执行中、成功、失败、已取消；
- 单设备输出详情；
- 失败设备重试；
- 导出批量命令结果。

批量执行默认逐设备串行，保持现场设备压力可控；并发度作为后续扩展，不与 v2.10 的重启闭环同时引入。

## 8. 错误与取消语义

- 认证失败、权限不足、命令拒绝：确定性失败，不自动无限重试。
- 连接超时、连接重置、瞬时网络错误：按配置重试。
- 用户取消：停止派发新设备，当前适配器在安全检查点退出，剩余设备标记为已取消。
- 重启命令导致的连接断开：根据“已发送/已确认”状态区分正常重启与发送前失败。
- 所有回调使用代际令牌或任务生命周期守卫，避免 UI 销毁后的悬空回调。

## 9. 测试与验收

### 单元测试

- 命令列表规范化和空命令拒绝；
- Telnet/SSH 协议选择与默认端口；
- 单设备多命令顺序执行；
- 瞬时网络错误重试，认证错误不重试；
- 取消后不再派发新设备；
- 重启命令发送后断开被识别为“重启已触发”；
- 部署失败设备不会收到重启命令。

### 集成验收

- 3 台设备批量下发 `uname -a`，逐设备显示结果；
- 3 台设备部署后仅对成功设备发送 `reboot`；
- Telnet 与 SSH 各完成一次批量命令和部署后重启；
- 一台设备瞬时断网时可重试，其余设备结果不受影响；
- 取消任务后无后台线程继续写 UI；
- Release 构建、CTest 和现场设备复测通过。
