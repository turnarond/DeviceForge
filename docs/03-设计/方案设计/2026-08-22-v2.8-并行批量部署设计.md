# DeviceForge v2.8 并行批量部署方案设计

## 1. 背景与动机

产品核心主张是把工业运维做成**多设备批量执行**。当前部署链路（FTP/SFTP 批量）功能完备，但批量本质是**串行逐台**：10 台 × 5 分钟 ≈ 50 分钟等待，这是与竞品拉开代差的最后一步，也是效率诉求的直接来源。

现有代码对并发化已有两处预留：
- `MultiProgressWidget` 注释自述"多设备并行部署进度组件"，per-device 接口全部为空实现（`{}`）——UI 契约已定，待实装；
- 部署循环每台设备经 `ProtocolRegistry.create()` 创建**独立 adapter 实例**，协议栈层天然隔离，无共享连接状态。

## 2. 目标 / 非目标

### 目标

| # | 目标 | 验收 |
|---|------|------|
| G1 | 部署循环并发化，并发度可配（1-8），默认值见 §8 | 10 台设备部署墙钟时间随并发度近线性下降 |
| G2 | 每设备独立进度 + 状态（MultiProgressWidget 空壳转正） | UI 实时显示各台百分比与成功/失败/取消态 |
| G3 | 部署报告导出 CSV + HTML（成功/失败/耗时/失败文件清单） | 一键导出，售后可直接归档 |
| G4 | 失败设备一键重试（仅重跑失败集合） | 重试复用原部署参数，结果并入日志 |
| G5 | 取消传播改为 per-device 标志（实现层），对外仍一键全局取消 | 触发取消后：未开始台次跳过、进行中台次按协议栈取消点中止、已完成台次结果保留；单台被中止不影响他台已产出结果 |

### 非目标（YAGNI）

- 断点续传 / 差量上传（文件级 md5 比对已有独立能力）
- 部署任务队列持久化与定时部署
- per-device 差异化协议参数（同一次部署所有设备同协议/端口/FTPS 开关，维持现状）
- ToolHost 多 Tool 并发（中期独立立项，本方案不动 ToolHost）

## 3. 现状解剖（startUpload 串行骨架）

```
QtConcurrent::run {                       // 后台线程，UI 不冻结 ✓
  for (device : m_devices) {              // ← 串行瓶颈点
    adapter = ProtocolRegistry.create(protocol);   // 每台独立实例 ✓
    deployable = dynamic_cast<IDeployable*>(adapter);
    adapter->connect(device, auth);
    clearRemoteDirectory?();              // 可选
    deployable->setCancelFlag(&m_cancelled);       // ← 共享单一标志
    deployable->setProgressCallback(pct → 全局总进度); // ← 串行语义
    for (file : localFiles) upload...;
    adapter->disconnect();
    successes/failures.push_back(deviceKey);
  }
  rebootAfterDeploy?();                   // TODO 占位（未实现）
  m_finishedCb(ok, successes, failures);
}
```

关键约束（来自 `IDeployable.h` 契约）：`setCancelFlag(std::atomic<bool>*)` 的 flag **必须存活至传输结束**，部署期间不得释放/修改指针内容。

## 4. 总体设计

### 4.1 组件划分

```
FtpDeployWidget                    FtpDeployBackend                    新增
┌──────────────┐   startUpload   ┌──────────────────┐   schedule   ┌─────────────────┐
│ 多进度视图    │ ←─ callbacks ── │  保持对外 API     │ ───────────→ │ DeploymentRunner │
│ (空壳转正)   │                 │  (签名不变)       │              │  (私有 QThreadPool)
│ 报告导出按钮  │                 │                  │              ├─────────────────┤
│ 重试失败按钮  │                 └──────────────────┘              │ DeployJob ×N     │
└──────────────┘                                                  │ (QRunnable)      │
                                                                  └─────────────────┘
新增纯逻辑（TDD 主战场）：DeviceResult / DeployReport / renderCsv() / renderHtml()
```

- **DeployJob**（QRunnable）：封装单台设备的完整部署事务——持有一个 `std::shared_ptr<IProtocolAdapter>`、独立的 `std::atomic<bool> m_cancelled`（job 存活期 = flag 存活期，满足 IDeployable 契约）、per-device 进度换算与带 `[ip:port]` 前缀的 logSink。产出 `DeviceResult`。
- **DeploymentRunner**：持有私有 `QThreadPool`（`setMaxThreadCount(concurrency)`，不用全局池以免与其他功能争抢），提交 N 个 DeployJob，`waitForDone()` 后聚合 `DeployReport`，触发既有 `m_finishedCb(ok, successes, failures)`（**对外回调签名不变**）。
- **FtpDeployBackend.startUpload**：签名与调用方零改动；内部从串行 for 循环换成 Runner 调度。`concurrency` 从 ConfigStore 读（键 `deploy.concurrency`）。

### 4.2 并发模型与取消语义

- 私有 QThreadPool，worker 数 = `min(concurrency, 设备数)`；
- 全局取消（工具栏/MultiProgress 取消钮）：遍历所有未完成 job 将其 `m_cancelled` 置 true——各协议栈已有的取消检查点（curl 进度回调返回非零 / SFTP 每文件前检查）立即生效；
- **单设备失败不影响他台**（现状 continue 语义自然保留）；已完成设备的结果不受后续取消影响；
- `m_uploadFuture.isRunning()` 防重入守卫保留；Backend `OnStop`/析构增加「cancel-all + wait」兜底，杜绝后台线程持有 `this` 悬垂（长稳审计点，见 §7）。

### 4.3 进度聚合

- DeployJob 内包装 adapter 的单文件 0-100 回调：`devicePct = (doneFiles * 100 + curPct) / totalFiles`；
- Runner 聚合总进度：`overall = Σ devicePct / N`（原子累加，节流 100ms 上报一次防 UI 刷屏）；
- MultiProgressWidget：实装 `setDeviceProgress(key,pct)` / `setDeviceStatusByKey(key,ok)` / per-device 行渲染；`setDeviceInfo/setDeviceStatus/rebuildUi` 若确认无用则删除（不留死接口）。

### 4.4 日志

logSink 统一注入 `[deviceKey]` 前缀（改造点集中在 DeployJob 一处，循环体业务代码不动）。日志脱敏纪律不变（只记方向/字节数/文件名，不记内容）。

### 4.5 部署报告（G3/G4）

```cpp
struct DeviceResult {
    std::string deviceKey;      // ip:port
    enum State { Ok, Failed, Cancelled } state;
    std::vector<std::string> failedFiles;   // 失败文件相对路径
    std::string lastError;                   // 适配器错误摘要
    long long durationMs; std::time_t startedAt;
};
struct DeployReport { std::string protocol; int concurrency;
                      std::vector<DeviceResult> results; };
// 纯函数 → tests/deploy 直测，零网络依赖
std::string renderReportCsv(const DeployReport&);
std::string renderReportHtml(const DeployReport&);
```

UI：部署结束后报告按钮可用；CSV 供 Excel 归档、HTML 含着色结果表。"重试失败设备"按钮：Widget 缓存上次请求参数 + 失败 deviceKey 集合，过滤后走同一 `startUpload` 入口（无新代码路径）。

## 5. 数据流

```
选中设备+文件 → bindDevices/bindCredentials → startUpload(参数不变)
  → Runner(concurrency from ConfigStore)
      → Job₁..Jobₙ 并行 [connect→clear?→upload×k→disconnect]
      → 各自 DeviceResult → 聚合 DeployReport
  → m_finishedCb(ok, successes, failures)   // 签名不变，Widget 无感升级
  → UI: 状态点着色 + 报告按钮点亮 + 重试按钮点亮(有失败时)
```

## 6. 错误处理

| 场景 | 行为 |
|---|---|
| 适配器创建失败 / 不支持部署能力 | 该台记 Failed，其余继续（现状语义） |
| 连接失败 / 清空失败 | 连接失败记 Failed；清空失败降级告警继续上传（现状语义） |
| 单文件失败 | 该台最终 Failed，failedFiles 记录明细，继续余下文件（现状语义） |
| 用户取消 | 未开始台次跳过（Cancelled 态），进行中台次按协议栈取消检查点中止 |
| 本地文件消失 | 记录该文件失败（现状语义），并发下多台同报属预期 |

## 7. 长稳审计点（开发规范第 14 条）

1. adapter 生命周期归 DeployJob 独享（shared_ptr），run() 末尾保证 disconnect，异常路径 RAII 兜底；
2. 回调捕获 `this`（Backend）的悬垂风险：OnStop/析构执行 cancel-all + pool.waitForDone() 后才放行基类析构；
3. 多线程同时读同一本地文件：只读 fopen 安全，无需加锁；禁止任何写入本地源文件的路径；
4. UI 回调全部经既有 QueuedConnection 编组模式（connectBackendSignals 现成管道）；
5. 并发压测验收：16 台模拟目标（本地 ftpd 循环）连续 50 轮无句柄增长（Task Manager 句柄数基线对比）。

## 8. 配置与兼容性

- ConfigStore 新键：`deploy.concurrency`（int，1-8）。**默认 1 = 与现行串行行为完全一致**（升级零惊扰）；设置面板（SettingsDialog）暴露滑块并附注「嵌入式 FTP 服务器注意最大连接数限制，建议 2-4 起步」。
- 对外 API（startUpload 三回调）签名不变 → FtpDeployWidget 改造限于 MultiProgress 实装与两个新按钮。
- IDeployable 接口零改动 → SshAdapter/FtpAdapter 无需修改（ABI 安全）。
