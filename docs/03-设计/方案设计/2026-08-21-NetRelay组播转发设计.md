## 1. 背景与现状评审结论

### 1.1 当前组播能力（2026-07-10 设计，已落地）

| 能力 | 状态 | 实现 |
|---|---|---|
| 组播抓收（零影响旁路抄收） | ✅ | `bind(AnyIPv4, port, ShareAddress\|ReuseAddressHint)` + `joinMulticastGroup(group, iface)` → 单向 Upstream |
| 录制 `.nrec`（protocol=2，组地址/端口入 reserved 区） | ✅ | RelayRecorder/RelayRecording |
| 回灌原组（离线按原时序） | ✅ | RelayPlayer Multicast 分支 |
| **实时转发**（抓收同时转给其他组/消费者） | ❌ **缺失** | 设计时 YAGNI 排除 |

### 1.2 使用性问题诊断（「不会用、不好用」根因）

| # | 问题 | 位置 |
|---|---|---|
| 1 | 协议下拉选 Multicast 后**界面零变化**：监听地址/端口仍显示可编辑（实际被忽略），组播组地址藏在「上游地址」框、标签不切换 | NetRelayWidget 无 `currentIndexChanged` 联动 |
| 2 | 回放面板「消费者 127.0.0.1:9001」默认值误导：组播回放默认回灌原组，但 UI 诱导填单播地址（非空则**覆盖**回灌目标为单播） | NetRelayWidget 回放区 + RelayPlayer 目标覆盖逻辑 |
| 3 | 会话列表组播固定一条（ID=1、恒 Upstream），展示意义弱 | Backend 组播路径不建会话 |
| 4 | **无转发入口**：用户期望"抓的同时能转"，当前只能抓 | 见 §2 |

## 2. 转发能力设计（本次核心）

### 2.1 转发形态（需用户确认）

| 形态 | 语义 | 零影响 | 主要风险 | 建议 |
|---|---|---|---|---|
| **M→U**：组播→单播 | 抓 A 组同时转发给指定单播消费者（如：仿真设备/不在组播域的机器） | **保持**（不改组播源，指定消费者单独收） | 单播流量放大；消费端需知地址 | 实现简单、风险低，**推荐优先** |
| **M→M**：组播→组播 | 抓 A 组同时转发到 B 组（如：A 组数据供 B 组测试台消费） | **破坏**（工具成为 B 组的源；B 组有真实源则混叠；A→B→A 环路风险） | 混叠/环路 | 可选扩展，需确认目标组无真实源 |
| 录制→回灌（已有） | 离线回放，非实时转发 | 离线 | 源在线混叠（已有提示） | 保持 |

> **「能转发则转发」落地建议**：M→U 为默认实现（低风险、贴合"转发给需要的消费者"），M→M 为可选扩展（需确认目标组无真实源）。两者共用同一转发通道（收到数据报 → 可选写往单播地址 / 组播地址），转发开关 UI 勾选。

### 2.2 转发通道设计（Backend）

```cpp
// 抓收增强：增加转发目标（可空）
struct CaptureForward {
    bool          enabled = false;
    QHostAddress  target;        // 单播 IP 或组播组地址（M→U / M→M）
    quint16       port = 0;
    QNetworkInterface iface;     // 转发用网卡（组播转发 join 目标组用；单播可空）
};

void NetRelayBackend::startCapture(RelayProtocol proto /*Multicast*/,
                                   const QString& groupAddr, quint16 port,
                                   const QString& ifaceAddr,
                                   const CaptureForward& forward);   // 新增参数
```

- **转发实现**：`onCaptureReadyRead()` 收包后，若 `forward.enabled`：`m_forwardSocket->writeDatagram(data, forward.target, forward.port)`
  - M→U：普通 `QUdpSocket` 直发单播目标
  - M→M：`QUdpSocket` + `joinMulticastGroup(forward.target, forward.iface)`（**加入目标组才能发组播**——Windows 发组播需先 join 目标组，否则丢弃）——这是 M→M 的关键实现细节
- **转发与抓收共用同一 socket 收包**，转发是"收 → 写"直通（不排队、不背压——UDP 无连接，writeDatagram 失败即丢，与抓收旁路语义一致）
- **互斥**：转发属于 `Relaying` 模式（与回放互斥，复用 `RelayMode`）
- **安全**：M→M 时 UI 二次确认（目标组可能被真实源占用/环路）；转发目标地址 fail-closed 校验

### 2.3 转发与录制/回放的关系

```
抓收(join A组) ──收包──▶ Hex 显示
        │
        ├──▶ 录制 .nrec（可选）
        ├──▶ 转发到 B组/单播（可选，M→U 或 M→M）
        └──（停止后）──▶ 回灌（离线，RelayPlayer）
```

- 转发是抓收的**实时旁路**，与录制并行不互斥
- 回放（RelayPlayer）与转发互斥（RelayMode 状态机）

- **不变**（protocol=2 组播，reserved 区存组地址/端口）
- 转发不改变录制内容（录的是抓收到的原始流，不含转发目标信息）
- 无需版本变更

## 6. 测试策略

- **单元**：转发目标地址校验（单播/组播/非法）纯逻辑用例（可入 tst_nrec 或独立 tst）
- **端到端（手动/半自动）**：
  1. 本机组播发送器往 A 组发包 → 工具抓收 + 录制 ✅
  2. 勾选转发 M→U：单播接收器实时收到一致数据，抓收/录制不中断 ✅
  3. 勾选转发 M→M（如有）：B 组接收器收到一致数据 ✅
  4. 零影响：工具抓收期间第三方接收器仍正常收包 ✅
  5. 长稳：转发 + 抓收 + 录制重复启停，内存/句柄曲线平稳
- **回归**：ctest 全量（15 目标）+ 组播旧 `.nrec` 读取

## 7. 风险与对策

| 风险 | 对策 |
|------|------|
| M→M 转发目标组被真实源占用 → 混叠 | UI 二次确认 + 文档警示；转发目标可空（仅 M→U 或仅抓收） |
| Windows 发组播需先 join 目标组 | M→M 转发 socket 必须 joinMulticastGroup(target)；文档记录 |
| 转发放大流量 | 转发为人工配置 + 明确告知；非默认开启 |
| 转发丢包（UDP 无背压） | 与抓收旁路语义一致（丢包属 UDP 本性），日志计数可选 |

## 8. 非目标（YAGNI）

- 广播、IPv6、二层组播、单播→组播、源在线检测/自动防混叠
- 转发缓冲/重传/可靠传输（UDP 语义）
