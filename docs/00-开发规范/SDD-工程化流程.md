# SDD 工程化流程

> 产品工程化流程（规范第 16 条）：**需求 → 方案设计 → 任务规划 → 实施 → 交付**，关键阶段专家评审（尤其方案设计）。
> 每个阶段定义：输入 / 活动 / 输出 / 评审门。评审不过不进入下一阶段。

---

## 阶段 0：需求分析

- **输入**：用户诉求、issue、市场反馈
- **活动**：需求澄清、边界定义（In/Out）、验收标准（可测）、优先级（P0/P1/P2）、长稳/性能要求、兼容性要求
- **输出**：需求文档 → `02-需求分析/2026-08-21-<标题>.md`（模板见 `02-需求分析/README.md`）
- **评审门**：需求评审——范围、优先级、验收标准达成一致，**关联 issue 建立**（需求变更同样走此门）

## 阶段 1：方案设计

- **输入**：已评审通过的需求文档
- **活动**：
  - 架构影响分析（分层 / 生命周期 / 并发 / 配置 / UI）
  - 方案选型与对比；接口设计（与既有接口一致性）
  - 兼容性分析（SDK ABI / 头文件向前兼容，见规范第 13 条）
  - 长稳设计（内存 / 句柄 / 连接释放路径，见规范第 14 条）
  - 测试策略（TDD 用例清单、边界用例、长稳用例）
  - 需同步更新的文档清单
- **输出**：设计文档 → `03-设计/方案设计/2026-08-21-<标题>-设计.md`
- **评审门**：**方案设计评审（专家评审，强制门禁）**——按 `评审检查单.md` 逐项核对；**不通过不得进入开发**。涉及对外 SDK/接口变更时必须有 ABI 兼容性结论。

## 阶段 2：任务规划

- **输入**：已评审通过的设计文档
- **活动**：任务拆分（每个任务附带对应测试）、依赖排序、里程碑与验收点
- **输出**：计划文档 → `03-设计/实施计划/2026-08-21-<标题>.md`
- **评审门**：计划评审（复杂项目必须；简单任务可由方案设计评审覆盖）

## 阶段 3：实施

- **输入**：计划 + 设计文档
- **活动**：
  - 从 `main` 新建分支（`feature/xxx` / `fix/xxx`，见 `issue与分支规范.md`）
  - **TDD 红-绿-重构**（规范第 6 条）；代码与文档同步更新（规范第 2 条）
  - 测试全绿（`ctest -C Release --output-on-failure`）
- **输出**：代码 + 测试 + 文档同步更新
- **评审门**：代码评审（PR review）——整洁、架构、长稳、错误处理，按 `评审检查单.md` 核对；通过后合并回 `main`

## 阶段 4：交付（打包 + 验证 + 发布）

- **输入**：已合入 `main` 的代码
- **活动**：
  1. 构建（`build.bat` 或 CI）
  2. 冒烟验证：`tools/devtools/smoke.py`
  3. 全量回归：`ctest -C Release --output-on-failure`
  4. 版本号全仓同步 + 一致性校验：`tools/devtools/versioncheck.py`
  5. 打包（zip 发布包，含 Qt DLL / libcurl-x64.dll / libssh2.dll / Updater.exe）
  6. 更新 `CHANGELOG.md` / `RELEASE_NOTES.md`
  7. 打 tag：`git tag -a vX.Y.Z -m "..."`（含版本号 / 日期 / 变更摘要）
- **输出**：发布包 + tag + 版本文档
- **评审门**：发布评审——验收标准逐项确认，见 `01-白皮书/版本发布与Tag规范.md` 的发布清单

---

## 回退条件

- 任一审评门不通过 → 回到对应阶段修订后再评审；设计变更需同步修订需求/计划。
- 实施中发现设计缺陷 → 回阶段 1 修订设计并重新评审。

## 变更管理

- 需求变更：走阶段 0 需求评审 → 评估对设计/计划影响 → 必要时重新评审方案设计。
- 版本边界外的新需求：不混入当前版本，记入 roadmap / 下一版本需求（规范第 10 条）。
