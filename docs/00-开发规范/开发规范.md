# DeviceForge 开发规范（总纲）

> 状态：生效中 ｜ 初始化：2026-08-21（init 会话落地）
> 本文是项目开发的**强制行为准则**，所有代码与文档变更必须遵守。
> 配套文档：`SDD-工程化流程.md`、`评审检查单.md`、`issue与分支规范.md`、`../01-白皮书/版本发布与Tag规范.md`。

---

## 1. 语言：中文优先

- 交流（issue / PR / 评审 / 会话）与**所有文档**一律使用中文，专业术语（TDD、SDD、ABI、MVP、EventBus、FTP、Modbus 等）与论文/标准引述除外。
- 代码注释、提交信息使用中文（提交信息建议 `conventional commits` 前缀 + 中文说明，如 `fix(modbus): 修复 Holding 寄存器读取存储区错误`）。
- 标识符（类名/方法/变量）遵循代码规范使用英文，注释用中文。

## 2. 文档是唯一的对外接口，必须保持最新、不得腐败

- `docs/` 是**唯一权威来源**。代码与文档不一致、文档间相互矛盾、引用失效，均视为缺陷（文档腐败），发现即修。
- 任何改动若涉及需求、接口、设计、架构、手册、版本号，**必须在同一提交内**同步更新对应文档。
- **版本号全仓同步**：改版本号必须同步九个强制来源：`CMakeLists.txt`（唯一权威 `project(... VERSION ...)`）、`src/app/DeviceForge.rc`、`README.md`、`CHANGELOG.md`、`CLAUDE.md`、`docs/01-白皮书/白皮书.md`、`RELEASE_NOTES.md`、根 `ROADMAP.md`、`docs/01-白皮书/产品路线图.md`。必须运行 `tools/devtools/versioncheck.py`；任一来源缺失、无法解析或版本不一致均阻断。
- 不允许"过时残留"：发现双轨/重复文件/失效引用时立即合并清理（本次 init 已清理 docs 顶层英文残留与 `docs/superpowers/` 旧路径）。
- **历史归档说明**：`03-设计/方案设计`、`03-设计/实施计划` 中的历史文档为过程归档，其内部旧路径引用视为历史快照、不再维护；**活文档**（本目录、`01-白皮书/`、`02-需求分析/`、`04-使用手册/`、`05-部署文档/`）必须引用当前有效路径。

## 3. 文档目录：中文命名 + 排序

固定目录结构（新增内容归入对应目录，不新建平级目录）：

```
docs/
  00-开发规范/      开发规范、SDD 流程、评审检查单、issue 模板
  01-白皮书/        产品白皮书、产品路线图、版本发布与 Tag 规范
  02-需求分析/      需求文档（SDD 阶段 0 输入）
  03-设计/          方案设计/（阶段 1）、实施计划/（阶段 2）
  04-使用手册/      用户手册、接口参考、架构设计
  05-部署文档/      构建指南、部署文档、安全说明、调试指南、Qt 版本一致性说明
  06-运营与文章/    运营流程、articles/ 技术文章
  images/          界面截图等图片资源
```

- 文件夹、文件名用中文，数字前缀排序（`00-` 规范 → `06-` 运营）。
- 新文件命名：`2026-08-21-<主题>.md` 放入对应目录。

## 4. 分支规范

- 每次需求开发、变更、修复 issue **必须从 `main` 新建分支**：`feature/xxx`、`fix/xxx`、`docs/xxx`、`refactor/xxx`、`chore/xxx`（可附 issue 号，如 `fix/opcua-timeout#88`）。
- 禁止直接在 `main` 上堆叠未提交改动；**一个分支只做一件事**，不混入无关功能。
- 完成并验证后合并回 `main`（`--no-ff` 保留 merge commit），删除已合并分支。
- 详见 `issue与分支规范.md`。

## 5. 开发工具集（tools/，Python 系列配套工具）

- `tools/` 是配套工程工具的固定目录，拥有**独立工程架构**：包结构（`devtools/`）+ 单元测试（`tools/tests/`，unittest 标准库）+ `README.md`，零第三方依赖。
- 开发过程中按工程需要新增工具（测试、部署、冒烟、一致性校验等）时，在 `tools/` 中实现并**自带测试**。
- 现有工具：
  - `versioncheck.py`：九个强制来源的版本一致性校验（CMake / RC / README / CHANGELOG / CLAUDE / 白皮书 / Release Notes / 根 Roadmap / 产品 Roadmap）
  - `smoke.py`：UI 冒烟（启动 exe → 校验主窗口出现 → 退出）
- 统一入口：`tools/devtools/cli.py`；运行测试：`python -m unittest discover -s tools/tests -v`。

## 6. TDD：永远遵循红-绿-重构循环

- 所有功能开发遵循 **红（先写失败测试）→ 绿（最小实现通过）→ 重构（保持绿）** 循环。
- **每次请求实现，必须附带对应的测试代码，或指明要让它变绿的测试用例**；禁止无测试的功能提交。
- 红灯（测试失败）代码不允许提交、不允许合入。
- C++ 侧用 QtTest/CTest（`tests/`，`ctest -C Release --output-on-failure`）；Python 工具用 unittest（`tools/tests/`）。

## 7. 代码整洁（《代码整洁之道》）

- 单一职责、命名表达意图、函数短小、DRY 无重复、注释解释"为什么"而非"是什么"。
- 提交前自查：无死代码、无调试残留（`qDebug` 临时代码/断点）、无大段注释掉的代码、无魔法数字。

## 8. 架构整洁（《架构整洁之道》），并全局考虑

- **依赖方向**：UI → 业务 → 适配器/基础设施，核心业务不依赖 UI 与第三方细节；外层依赖内层，禁止反向。
- **全局考虑**：新功能先评估对既有架构的影响（分层、生命周期、并发模型、配置持久化、UI 布局），改动前先出方案设计（见 SDD），不"局部舒服、全局别扭"。
- 复用既有机制：服务生命周期用 `lwserverbase`（ServiceTask/ServiceManager）、跨线程解耦用 `lwmsgq`、协议统一走 `IProtocolAdapter`/`ProtocolRegistry`、配置走 `ConfigStore`（SQLite + DPAPI）、UI 主题走 QSS 双主题体系——**不得绕开**。

## 9. 发现的问题及时记录（当前没时间改也要留下痕迹）

- 开发中发现的、当前无时间修复的问题：**立即提 issue 到仓库**（哪怕一句话：现象 + 位置 + 影响），或记入 `03-设计/问题记录/`。
- 临时规避（workaround）必须在代码注释中写明 `workaround + issue 链接`，禁止无声规避。

## 10. 白皮书 / roadmap / 版本边界 / Tag

- 产品总体白皮书：`01-白皮书/白皮书.md`；路线图：`01-白皮书/产品路线图.md`。
- **每个版本必须有明确边界**：版本目标、范围（In/Out）、验收标准，在发布计划中定义，打包前逐项核对。
- **打包节点必须同步在 git 仓库打 tag**（`vX.Y.Z`，annotated tag），tag 消息标注版本号、发布日期、变更摘要。
- 详见 `01-白皮书/版本发布与Tag规范.md`。

## 11. 不解决非本工程的问题

- 排查可以，但**不要**把不属于本工程的修复混入本工程提交（会污染本工程、掩盖供应商责任）。
- 上游工程 / SDK / 文档供应商的问题：通过 issue 提给对方（用 `issue模板.md` 中的供应商模板），本工程记录引用与状态即可。

## 12. 重构：先讨论、再动手

- 触发条件：新增/修改功能时，与当前整体架构冲突较大、影响面大，或改动别扭、不方便时，**考虑重构**。
- 流程：**讨论**（动机 / 影响面 / 兼容性 / 回滚方案）→ 重构方案文档 → 评审通过 → 独立 `refactor/xxx` 分支实施。
- 重构不与功能开发混在同一分支；重构后必须全量回归（ctest + 冒烟）。

## 13. SDK 库的向前兼容（ABI 约束）

- 若对外提供 SDK 库给用户使用，版本升级涉及头文件/接口改动时**必须向前兼容**。
- 避免二进制 ABI 不匹配：不修改已有导出函数签名、类成员布局、虚表顺序；新能力优先**新增接口**而非改旧接口。
- 必须的不兼容变更：提升 MAJOR 版本 + 提供迁移说明，杜绝使用者被迫用新 SDK 重编。

## 14. 长久运行稳定性（内存泄漏 / 句柄泄漏）

- 分析、评审、测试时**必须考虑长稳**：内存泄漏、句柄（socket/文件/窗口）泄漏、连接泄漏、线程安全、定时器与回调泄漏。
- 长稳验证方法：长时间运行 + 监控内存/句柄曲线；重复连接-断开循环；`ctest` 回归；Linux 用 ASan/Valgrind，Windows 用 VS 诊断工具/Dr. Memory。
- 具体检查项见 `评审检查单.md` 的长稳部分。

## 15. Debug（有条件就调试）

- 有条件时使用调试器定位问题：**Windows 用 cdb**（WinDbg 命令行工具），**Linux 用 gdb**。
- Windows 上不好调的问题，**可以转到 WSL** 复现与调试。
- 崩溃类问题：抓 dump（cdb `-z` 离线分析 dump / `.dump` 命令），分析调用栈定位根因；提交修复时附根因说明。

## 16. SDD 工程化流程（需求 → 方案设计 → 任务规划 → 实施 → 交付）

- 产品工程化必须走 **SDD**：需求分析 → 方案设计 → 任务规划 → 实施 → 交付。
- **关键阶段必须有专家评审，尤其是方案设计评审**（强制门禁，不过不进入开发）。
- 每阶段有输入/活动/输出/出口准则，详见 `SDD-工程化流程.md` 与 `评审检查单.md`。
